# Contributing

It is highly recommended to follow a similar process as described in the documented [Ansible Development Cycle](https://docs.ansible.com/ansible/devel/community/development_process.html).

## pre-commit

To help ensure high-quality contributions this repository includes a [pre-commit](https://pre-commit.com) configuration which
corrects and tests against common issues that would otherwise cause CI to fail.

### Installation

Follow the [pre-commit-instructions](https://pre-commit.com/#install) provided with pre-commit and run `pre-commit install` under the repository base.

If for any reason you would like to disable the pre-commit hooks run `pre-commit uninstall`.

### Running pre-commit checks

You can trigger it locally with `pre-commit run --all-files` or even to run only for a given file `pre-commit run --files YOUR_FILE`.

## Documentation

The documentation conventions live in [`AGENTS.md`](https://github.com/snapp/ansible-collection-soe/blob/main/AGENTS.md): terminology, the collection and role README structure, the argument spec and `meta/main.yml` rules, and the shared inventory variable contract. Read it before touching a README or a `meta/` file.

Every role has a `meta/argument_specs.yml`, and that spec is the single source of truth for the role's variables. The "Role variables" section of each role README is generated from it:

```console
python3 tools/render_role_docs.py              # render every role README
python3 tools/render_role_docs.py caddy        # render one role
python3 tools/render_role_docs.py --check      # verify; this is what the role-docs pre-commit hook runs
```

When you add or change a variable:

1. Add or change it in `defaults/` (a value) or in the tasks (an input read without a default).
2. Mirror it in `meta/argument_specs.yml`: the spec `default` must equal the `defaults/` value literally, Jinja included; inputs without a default get no `default` and a description of the behaviour when unset; secrets get `no_log: true` and the word "Secret".
3. Run `python3 tools/render_role_docs.py <role>` and commit the regenerated README together with the spec.
4. Update the hand-written README sections (composition, tags, security, operational notes) and, for a new shared un-namespaced variable, the "Shared inventory variables" table of the collection README.

The `--check` mode fails on a README that is out of date, on a `defaults/` key missing from the spec, on a spec default that differs from `defaults/`, on specified internal variables, on "Defaults to" prose, on a `short_description` ending with a period, on a `meta/main.yml` description that differs from the spec, and on relative links or invalid GitHub alert types in a README. Links in READMEs must be full URLs because they are rendered outside the repository.

## Changelog fragments

The changelog is generated by [antsibull-changelog](https://ansible.readthedocs.io/projects/antsibull-changelog/). Every user-visible change needs a fragment in `changelogs/fragments/<short-slug>.yml`, named after the change, with one or more of the sections configured in `changelogs/config.yaml`:

```yaml
---

minor_changes:
  - redhat_satellite - the role now manages host collections with the ``redhat.satellite.host_collection`` module.

bugfixes:
  - redhat_cockpit - the certificate stage read ``redhat_cockpit_idm_service_tls_request_id`` instead of the defined ``redhat_cockpit_idm_service_request_id``.
```

Entries start with the role or area name, a dash, and one or more full sentences in ReStructuredText (double backticks for literals). Use `breaking_changes` for anything a site repository must change to keep working (renamed variables or tags, new required inputs, changed defaults), `bugfixes` for corrected behaviour, `minor_changes` for new features and new argument specs, and `trivial` for changes that need no release note. Check fragments with `antsibull-changelog lint`.

## Release Workflow

Ensure that you increment the version tracked in the `galaxy.yml` file before committing the release, then run `antsibull-changelog release` to fold the fragments into `CHANGELOG.rst` and `changelogs/changelog.yaml`.
