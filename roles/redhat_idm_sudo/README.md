# Ⓐ Ansible Role: redhat_idm_sudo

Creates or updates sudo rules in Red Hat Identity Management (IdM) with `redhat.rhel_idm.ipasudorule`. Centrally managed sudo is what lets the reference implementation remove the local bootstrap account and its `/etc/sudoers.d` entry after IdM exists: the automation account and the site administrators keep their privileges through an IdM rule that SSSD enforces on every enrolled host, and no host carries a local privilege grant.

The role is composed by `infra.soe.redhat_identity_management` during the configure stage, right after IdM is installed.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.redhat_idm_sudo` when referencing this role.

## Requirements

- Managed node: a Red Hat Enterprise Linux (RHEL) 9 or 10 host that is an IdM server or an enrolled client with the IdM Python libraries, because the `redhat.rhel_idm` modules run on the target.
- Collections used directly: [`redhat.rhel_idm`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_idm/) (`ipasudorule`).
- An IdM administrator password in `redhat_idm_sudo_admin_password`. Users and groups referenced by a rule must exist.

## Dependencies and composition

The role composes nothing. It is composed by [`redhat_identity_management`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_identity_management/README.md), which passes `redhat_idm_sudo_admin_password` ← `redhat_identity_management_admin_password`; `redhat_idm_sudo_rules` comes from inventory.

## Tags

The role defines no tags. `redhat_identity_management` applies `idm_sudo` and `idm_configure`.

## Example playbook

```yaml
---

- name: Red Hat Identity Management (IdM) sudo rules
  hosts: "{{ target_hosts | default('idm_server') }}"
  gather_facts: false
  become: true
  roles:
    - role: infra.soe.redhat_idm_sudo
      redhat_idm_sudo_admin_password: "{{ idm_admin_password }}"
      redhat_idm_sudo_rules:
        - name: allow_all
          description: Site administrators and the automation account may run any command as any user
          runasusercategory: all
          runasgroupcategory: all
          hostcategory: all
          cmdcategory: all
          users:
            - ansible
            - siteadmin
          options:
            - '!authenticate'
```

## Security considerations

- A rule with every category set to `all` and `!authenticate` is equivalent to `ALL=(ALL) NOPASSWD: ALL`; restrict it to the automation account and named administrators, and prefer command groups for everyone else.
- The administrator password is passed as `ipaadmin_password`; the task runs under `no_log` (gated by `no_log_enabled`), which also hides the rule definitions.
- Rules are only ever ensured present; stale rules must be removed by hand.

## Operational notes

- SSSD caches sudo rules; a new rule takes effect on a host after the cache refreshes (`sss_cache -E` forces it), which is why `redhat_identity_management`'s cleanup stage flushes SSSD before it removes the bootstrap account.
- `sudo -l -U <user>` on an enrolled host shows the effective rules; `ipa sudorule-show <name>` shows the definition.
- Using the rule for the automation account is what makes `become: true` work for Ansible after the local bootstrap sudoers file is gone.
