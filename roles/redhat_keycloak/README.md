# Ⓐ Ansible Role: redhat_keycloak

Installs Red Hat build of Keycloak (RHBK) with `redhat.rhbk.rhbk` under a local service account and configures it from the control node: the master and primary realms with `redhat.rhbk.rhbk_realm`, the OpenID Connect clients with the `rhbk_client` module, and client and service-account role mappings with the `community.general` Keycloak modules. When a Red Hat Identity Management (IdM) administrator password is available it first creates the `keycloak` automation account (the LDAP bind account for user federation), the `keycloak-admins` group and an HBAC rule in IdM, and requests the RHBK TLS certificate from the IdM certificate authority, owned by the service account. Firewall rules and SCAP remediation complete the host.

RHBK is the single sign-on layer of the reference implementation. IdM remains the source of identity: users and groups are federated from IdM LDAP and authenticated with Kerberos through the `redhat.rhbk` inputs, and RHBK issues the OpenID Connect tokens that Red Hat Ansible Automation Platform (AAP), Red Hat Satellite, the Caddy forward-auth sidecars (`infra.soe.caddy`) and NetBird (`infra.soe.netbird`) consume. The `groups` claim those clients authorise on is produced by the group mappers defined in `rhbk_clients`. RHBK is the ninth stage of `site.yml`, after Satellite and before Caddy.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.redhat_keycloak` when referencing this role.

## Requirements

- Managed node: Red Hat Enterprise Linux (RHEL) 9 or 10, registered for content (`infra.soe.redhat_register`), enrolled in IdM (`infra.soe.redhat_idm_register`), with `/opt` on its own volume if the site layout requires it (`infra.soe.local_storage`).
- Control node: network access to the RHBK API at `rhbk_url` and trust in the IdM CA, because the realm, client and role mapping tasks are delegated to `localhost`.
- Collections used directly: [`redhat.rhbk`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhbk/) (`rhbk`, `rhbk_realm` roles and `rhbk_client` module), [`community.general`](https://docs.ansible.com/ansible/latest/collections/community/general/index.html) (`keycloak_client_rolemapping`, `keycloak_user_rolemapping`); through composed roles, [`redhat.rhel_idm`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_idm/) and [`redhat.rhel_system_roles`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_system_roles/).
- Inventory groups: the host is in `keycloak`; an `idm_server` group when the IdM stages run.
- Inventory inputs of `redhat.rhbk` (`rhbk_version`, `rhbk_offline_install` and `rhbk_download_path` or the Red Hat Network credentials, `rhbk_hostname`, `rhbk_url`, `rhbk_https_port`, `rhbk_cert_file`, `rhbk_key_file`, `rhbk_user_federation`, `rhbk_realm`, ...), documented at the link above. The IdM certificate the role requests is what `rhbk_cert_file` and `rhbk_key_file` should point at.

## Example playbook

This matches the collection's own [`playbooks/redhat_keycloak.yml`](https://github.com/snapp/ansible-collection-soe/blob/main/playbooks/redhat_keycloak.yml):

```yaml
---

- name: Red Hat Build of Keycloak (RHBK)
  hosts: "{{ target_hosts | default('keycloak') }}"
  gather_facts: false
  become: true
  tags:
    - redhat
    - keycloak
  roles:
    - infra.soe.redhat_keycloak
```

A client for an application fronted by a Caddy forward-auth sidecar, in `group_vars/keycloak`:

```yaml
rhbk_url: "https://{{ inventory_hostname }}"
rhbk_clients:
  - realm: "{{ keycloak_primary_realm }}"
    name: Code Server
    client_id: code-server
    public_client: false
    client_authenticator_type: client-secret
    secret: "{{ _vault_code_server_oauth_client_secret }}"
    redirect_uris:
      - https://code.mtj1.prod.example.org/oauth2/callback
    standard_flow_enabled: true
    protocol_mappers:
      - name: groups
        protocol: openid-connect
        protocolMapper: oidc-group-membership-mapper
        config:
          claim.name: groups
          full.path: false
          id.token.claim: true
          access.token.claim: true
      - name: code-server-audience
        protocol: openid-connect
        protocolMapper: oidc-audience-mapper
        config:
          included.client.audience: code-server
          access.token.claim: true
```

## Security considerations

- The bootstrap administrator password installs RHBK and configures every realm; the role asserts it is set and never logs it. Rotate it after installation through the RHBK console and update the vaulted value.
- Client secrets in `rhbk_clients` are applied under `no_log` (gated by `no_log_enabled`), which also hides the client definitions from the output. Declaring a `secret` in inventory is what lets the same vaulted value be shared with the application's sidecar.
- The configure stage runs on the control node and authenticates against the master realm over HTTPS; the controller must trust the IdM CA, otherwise it has to be told not to verify, which is not recommended.
- The TLS key is owned by the service account (`rhbk`), because the RHBK process reads it directly; the `redhat.rhbk` inputs `rhbk_cert_file` and `rhbk_key_file` must point at `/etc/pki/keycloak_idm_service/`.
- The default firewall definition opens 443/tcp and the JGroups ports 7800/tcp and 57800/tcp. The JGroups ports are only needed between cluster members; restrict them to a cluster firewalld zone on single-node sites.
- The `keycloak` IdM account is the LDAP bind account for user federation. A dedicated IdM system account (`ipa sysaccount-add`) with a non-expiring password policy is the stricter choice; the defaults use a regular account and the comment in `defaults/main/identity_management.yml` records that.

## Operational notes

- Stage order: local service account → IdM users → groups → HBAC → certificate → install → configure → firewall → SCAP. The local account must exist before `redhat.rhbk.rhbk` runs, and the certificate before the HTTPS listener starts.
- `redhat.rhbk.rhbk` validates `rhbk_jgroups_bind_address` from the default IPv4 fact under the `always` tag, which is why the role gathers the `network` fact subset immediately before importing it; tag-filtered runs still work.
- `redhat_keycloak_idm_service_tls_enabled` and `redhat_keycloak_base_url` are defined but not consulted by any task; the certificate is always requested and the URLs come from the `redhat.rhbk` inputs.
- Both realms are configured on every run; `organizations_enabled` is set on the primary realm. Realm-level settings beyond those come from the `redhat.rhbk` inputs such as `rhbk_user_federation` and `rhbk_policies`.
- `rhbk_client` manages a fixed subset of client attributes; PKCE and device-authorization settings are passed through `attributes`, and service-account role grants need the role mapping lists.
- No SCAP tailoring is shipped for RHBK; set `redhat_keycloak_scap_tailoring_*` in inventory when the profile needs exceptions.
