# Ⓐ Ansible Role: redhat_ansible_automation_platform

Installs Red Hat Ansible Automation Platform (AAP) with the containerized installer under a dedicated rootless service account, using the `infra.aap_utilities` roles to download, prepare and run the installer, then imports the subscription manifest and dispatches the declarative configuration of gateway, controller, hub and Event-Driven Ansible objects from inventory through `infra.aap_configuration`. When a Red Hat Identity Management (IdM) administrator password is available it first creates the service account (with a subordinate ID range for rootless Podman), the `aap-admins` and `aap-users` groups and an HBAC rule in IdM, and requests the platform certificate from the IdM certificate authority so that every component serves an IdM-issued certificate. Firewall rules and AAP-specific CIS tailoring complete the host.

AAP is the twelfth stage of `site.yml`. It presupposes IdM (accounts, certificate), Satellite (content) and the Caddy reverse proxy that publishes it under its public name, and it is the control plane that afterwards runs this collection's playbooks as job templates against the site. A single containerized node carries every component; that is the hardware footprint speaking, not the design, and the installer inventory in `aap_setup_prep_inv_nodes` is where a site spreads components across hosts.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.redhat_ansible_automation_platform` when referencing this role.

## Requirements

- Managed node: Red Hat Enterprise Linux (RHEL) 9 or 10 sized per the AAP containerized topology, registered for content with the AAP repositories enabled (`infra.soe.redhat_register`), enrolled in IdM (`infra.soe.redhat_idm_register`), with a volume for the service account home (`/var/lib/aap`, `infra.soe.local_storage`).
- Collections used directly: [`infra.aap_utilities`](https://console.redhat.com/ansible/automation-hub/repo/validated/infra/aap_utilities/) (`aap_setup_download`, `aap_setup_prepare`, `aap_setup_install`), [`infra.aap_configuration`](https://console.redhat.com/ansible/automation-hub/repo/validated/infra/aap_configuration/) (`controller_license`, `dispatch`); through composed roles, [`redhat.rhel_idm`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_idm/) and [`redhat.rhel_system_roles`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_system_roles/).
- Inventory groups: the host is in `aap_installer`; an `idm_server` group when the IdM stages run.
- Inventory inputs of the upstream roles: the installer inventory (`aap_setup_prep_inv_nodes`, `aap_setup_prep_inv_vars` with the component passwords, registry credentials and TLS paths), the Red Hat API offline token (`aap_setup_down_offline_token`) and the `infra.aap_configuration` object lists (`gateway_*`, `controller_*`, `hub_*`, `eda_*`), all documented at the links above.
- A subscription manifest archive when `aap_manifest_import` is true.

## Security considerations

- During the installer stage the service account receives `ALL=(ALL) NOPASSWD: ALL` in `/etc/sudoers.d/<user>` (validated with `visudo`), and the file is removed in an `always` block whether or not the installer succeeded. The installer needs root for package installation; between runs the account has no privileges.
- The service account gets systemd lingering so the rootless Podman units survive logout, and its home outside `/home` is registered as `/home`-equivalent for SELinux so the container storage is labelled correctly.
- `aap_setup_ignore_preflight_errors: true` makes the role edit the installer's own `install.yml` to skip variable preflight checks. Use it only to work around a known false positive; the edit is reapplied on every run.
- Secrets flow through several inputs: the Red Hat offline token, the gateway admin password, every component password and registry credential inside `aap_setup_prep_inv_vars`, and the manifest. All belong in Ansible Vault or credential injectors; the role itself logs none of its own secret options.
- The default firewall definitions open 443/tcp and the component ports (5432, 6379, 8443 to 8446, 27199). The `redhat_aap_frontend` and `redhat_aap_internal` services exist so a site can expose only 443 on the user-facing firewalld zone and keep the component ports on an internal one.
- The shipped CIS tailoring deselects rules that break containerized AAP or unattended operation (GRUB password, root password requirement, `deny_execmem`, overlay module, unowned container-layer files, journald and rsyslog coexistence, SSH user limits). Each exception carries a justification in [`vars/scap/cis.yml`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_ansible_automation_platform/vars/scap/cis.yml).

## Operational notes

- Stage order: IdM users → groups → HBAC → certificate → install → configure → firewall → SCAP; the certificate must exist before the installer, because the installer inventory references its paths.
- `aap_setup_inst_force` is true by default, so every run re-executes the installer with the current inventory; that is the supported way to change installer settings, and it takes a long time. Use `--skip-tags aap_install` for configuration-only runs.
- The `redhat_idm_users` default enables a subordinate ID range for the service account; rootless Podman on the host depends on it and on `infra.soe.redhat_idm_register` having enabled SSSD subid.
- The configure stage reaches the platform API at `aap_routable_hostname`; `aap_gateway_validate_certs` defaults to false because the controller may not trust the IdM CA. Set it to true once it does.
- `infra.aap_configuration.dispatch` applies whatever object lists are defined in inventory and is idempotent; an empty object list means nothing is removed.
- The play runs with `any_errors_fatal`, so a failure on the installer host stops the whole play immediately.
