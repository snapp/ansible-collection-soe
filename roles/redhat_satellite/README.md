# Ⓐ Ansible Role: redhat_satellite

Installs Red Hat Satellite Server and configures it from inventory: the subscription manifest, organizations and locations, content credentials, repositories and sync plans, host collections, lifecycle environments, content views with version cleanup, activation keys, host groups, domains, realms, subnets, operating systems, provisioning templates and compute resources. When a Red Hat Identity Management (IdM) administrator password is available the role also creates Satellite's automation account, administrator and user groups and an HBAC rule in IdM, joins the Satellite realm proxy to the IdM realm so provisioned hosts are enrolled automatically, requests the Satellite web certificate from the IdM certificate authority and installs it with `satellite-installer`. Firewall rules and CIS-based SCAP remediation with Satellite-specific tailoring complete the host.

Satellite is the content and provisioning layer of the reference implementation. In the `site.yml` build order it follows IdM, IdM client enrolment and Cockpit, and it must exist before Red Hat build of Keycloak (RHBK), Red Hat Ansible Automation Platform (AAP) and RHEL image builder: content views gate every later package install, `infra.soe.redhat_register` registers hosts to it, and `infra.soe.redhat_image_builder` points its repositories at its Pulp content. One Satellite server without capsules is a single point of failure by hardware footprint, not by design; the role does not prevent adding capsules through the same `redhat.satellite` inputs.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.redhat_satellite` when referencing this role.

## Requirements

- Managed node: Red Hat Enterprise Linux (RHEL) 9 or 10 sized for Satellite Server, registered to the Satellite repositories so the `satellite` package resolves (`infra.soe.redhat_register` with the Satellite and Satellite maintenance repositories enabled), and enrolled in IdM (`infra.soe.redhat_idm_register`) when the IdM stages are enabled.
- Collections used directly: [`redhat.satellite`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/satellite/) (roles and the `host_collection` and `realm` modules), [`redhat.satellite_operations`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/satellite_operations/) (`installer` role); through composed roles also [`redhat.rhel_idm`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_idm/) and [`redhat.rhel_system_roles`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_system_roles/).
- Inventory groups: the host is in `satellite_server`; an `idm_server` group must exist because `infra.soe.redhat_idm_users` delegates its Kerberos login to its first member.
- Inputs of the upstream roles in inventory: `satellite_installer_*` for the installer (scenario, options, package) and the `redhat.satellite` role variables (`satellite_organizations`, `satellite_locations`, `satellite_content_credentials`, `satellite_products`, `satellite_sync_plans`, `satellite_lifecycle_environments`, `satellite_content_views`, `satellite_activation_keys`, `satellite_hostgroups`, `satellite_domains`, `satellite_subnets`, `satellite_operatingsystems`, `satellite_provisioning_templates`, `satellite_compute_resources`, `satellite_compute_profiles`, `satellite_settings`, `satellite_manifest_*`). Each upstream role documents its own variables at the links above; this role only adds the inputs listed below.
- A subscription manifest reachable by `redhat.satellite.manifest` when `satellite_manifest_import` is true.

## Security considerations

- The IdM administrator password is piped to `kinit` and `foreman-prepare-realm` through `ansible.builtin.shell`; both tasks run under `no_log` controlled by `no_log_enabled`. The `host_collection` and `realm` loops are `no_log` for the same reason, which also hides the loop items.
- The realm keytab is copied to `/etc/foreman-proxy/freeipa.keytab` with mode `0640`, owner `root`, group `foreman-proxy`. It grants the realm proxy the right to add and remove hosts in the IdM realm.
- The Satellite web certificate, key and CA come from `/etc/pki/<request id>/` owned by root; `satellite-installer --certs-update-server-ca` makes the IdM CA the trusted CA for every registered client.
- The default firewall definition opens 53/tcp+udp, 67/udp, 69/udp, 80/tcp, 443/tcp, 5646-5647/tcp, 5910-5930/tcp, 8000/tcp and 9090/tcp. Narrow it in `redhat_satellite_firewall` if provisioning services are not used.
- IPv6 is disabled on every interface except loopback through `/etc/sysctl.d/ipv6.conf`, as Satellite requires an IPv6 loopback address.
- The shipped CIS tailoring deselects rules that would break Satellite (`httpd` and `tftp-server` removal, `noexec` on `/tmp` and `/var/tmp`, the CIS crypto policy, SSH user limits, file-ownership checks and, for IdM-enrolled hosts, GSSAPI and the authselect profile). Each exception carries a justification and review date in [`vars/scap/cis.yml`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_satellite/vars/scap/cis.yml); review them before applying the profile elsewhere.

## Operational notes

- Stage order inside the role: IdM users → groups → HBAC → network → install → realm → certificate → configure → firewall → SCAP. The IdM stages run before the installer so that the automation account exists when Satellite's IdM authentication is configured.
- `network.yml` writes an `ANSIBLE SATELLITE SERVER` block into `/etc/hosts`, flushes handlers to apply the sysctl change and rebuilds the initramfs; a reboot is not forced.
- `install.yml` installs the `satellite` package and runs `redhat.satellite_operations.installer`. Re-running the role is the normal way to apply installer option changes; the installer is idempotent.
- The realm stage runs only once: it is skipped as soon as `/etc/foreman-proxy/freeipa.keytab` exists. Remove that file to redo the realm join.
- The certificate stage compares the SHA-256 of the IdM-issued certificate with `/root/ssl-build/<satellite_hostname>/<satellite_hostname>-apache.crt` and re-runs `satellite-installer --certs-update-server --certs-update-server-ca` on any difference, so a certificate renewed by certmonger is picked up on the next run. Handlers then wait for port 443 and assert that the served certificate contains `satellite_hostname`.
- `redhat.satellite.sync_plans` is not idempotent and reports a change on every run; `redhat.satellite.content_view_version_cleanup` also runs on every pass.
- `satellite_realms` gates two different things: the `realm` module calls in the configure stage and the realm-capsule join. Both need an IdM administrator password.
- SCAP tailoring ships for the `cis` profile only (`vars/scap/cis.yml`). For another profile, set `redhat_satellite_scap_tailoring_*` in inventory; `infra.soe.redhat_scap` reads `redhat_scap_profile` from inventory itself, so `redhat_satellite_scap_profile` normally mirrors it.
- The composed `redhat_idm_users` role logs in to IdM from the first `idm_server` host using the shared `idm_admin_password`, independently of `redhat_satellite_idm_admin_password`. Keep both set to the same secret.
