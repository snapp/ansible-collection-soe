# Ⓐ Ansible Role: redhat_idm_service

Registers a Kerberos service principal in Red Hat Identity Management (IdM) for a host and, when TLS is enabled, requests a certificate for that principal from the IdM certificate authority through certmonger. The certificate, private key and a copy of the IdM CA chain are kept under a directory owned by the service account, where the product roles pick them up: Red Hat Satellite hands them to `satellite-installer`, Red Hat build of Keycloak (RHBK) serves them on its HTTPS listener, Red Hat Ansible Automation Platform (AAP) passes them to the containerized installer and Cockpit uses them for its web console. Names listed as Subject Alternative Names (SANs) inside the IdM domain also receive a DNS CNAME record and a principal alias, so a service can be reached under a stable alias such as `satellite.mtj1.prod.example.org` while the certificate stays bound to the host.

In the `site.yml` build order this role runs inside the Satellite, RHBK, Cockpit and AAP stages. It presupposes that IdM is installed (`infra.soe.redhat_identity_management`) and that the host is enrolled (`infra.soe.redhat_idm_register`), because `ipa-getcert` only works on an enrolled host. It is the mechanism behind the end-to-end TLS goal of the reference implementation: every service certificate is issued and renewed by the IdM CA, never self-signed.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.redhat_idm_service` when referencing this role.

## Requirements

- Managed node: Red Hat Enterprise Linux (RHEL) 9 or 10, enrolled in IdM with `certmonger` and `ipa-client` installed (both are present after `infra.soe.redhat_idm_register`).
- Collections used directly: [`redhat.rhel_idm`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_idm/) (`ipadnsrecord`, `ipaservice` modules).
- An IdM administrator password, supplied through `redhat_idm_service_admin_password` (composing roles pass their own `<role>_idm_admin_password`).
- The shared `idm_domain` inventory variable (see below).
- No inventory group is required; the role runs on the host that owns the service.

## Tags

The role defines no tags of its own. Composing roles apply `idm_service`, `idm_configure` and their product tag (`satellite_identity_management`, `keycloak_identity_management`, `aap_identity_management`, `cockpit_identity_management`) to the included tasks, so `--tags idm_service` selects every service-certificate stage across the site.

## Example playbook

This matches the collection's own [`playbooks/redhat_idm_service.yml`](https://github.com/snapp/ansible-collection-soe/blob/main/playbooks/redhat_idm_service.yml):

```yaml
---

- name: Configure Red Hat Identity Management (IdM) service integration
  hosts: "{{ target_hosts | default('redhat') }}"
  gather_facts: false
  tags:
    - redhat
    - idm_service
  roles:
    - infra.soe.redhat_idm_service
```

Composing the role for a service that runs under its own account and needs an alias:

```yaml
- name: Request the web certificate for a self-hosted service
  ansible.builtin.include_role:
    name: infra.soe.redhat_idm_service
  vars:
    redhat_idm_service_admin_password: "{{ idm_admin_password }}"
    redhat_idm_service_user: gitea
    redhat_idm_service_group: gitea
    redhat_idm_service_tls_enabled: true
    redhat_idm_service_tls_request_id: gitea_idm_service
    redhat_idm_service_tls_sans:
      - git.mtj1.prod.example.org
```

## Security considerations

- The administrator password is used by the `ipadnsrecord` task under `no_log` (gated by `no_log_enabled`) and by the `ipaservice` task, which relies on the module marking `ipaadmin_password` as `no_log` itself.
- The private key is written with mode `0600` inside a `0700` directory; the certificate is `0640` and the CA copy `0644`, all owned by `redhat_idm_service_user`:`redhat_idm_service_group`. Choose a dedicated service account rather than `root` wherever the service can read the files itself.
- Certificates are tracked by certmonger (`ipa-getcert request -r`), so renewal happens automatically as root. The role does not restart the consuming service after a renewal; see the operational notes.
- No ports are opened and no services are started other than `certmonger`.

## Operational notes

- The request is made idempotent by `creates: redhat_idm_service_tls_cert`. If the certificate file is removed but the certmonger request still exists, the role accepts the "already used by request" answer and continues; remove the stale request with `ipa-getcert stop-tracking -i <request id>` before re-requesting.
- The role waits up to 10 seconds (5 attempts) for the request to reach `MONITORING`. Slow CA responses show up here first; `ipa-getcert list -i <request id>` shows the current state.
- Renewal by certmonger replaces the files in place but does not notify the service. Satellite and AAP need their installers re-run to pick up a renewed certificate (the Satellite role does this when it detects a checksum change); RHBK and Cockpit reload on restart.
- SANs outside `idm_domain` are added to the certificate and the principal but do not get a CNAME record; create those records in the external DNS zone.
- `redhat_idm_service_fqdn` is the host name the certificate is issued for; when a service answers under several host names, keep the real host as the FQDN and list the aliases in `redhat_idm_service_tls_sans`.
