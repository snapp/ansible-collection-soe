# Ⓐ Ansible Role: redhat_scap

Remediates a Red Hat Enterprise Linux (RHEL) host against a SCAP Security Guide profile with `oscap xccdf eval --remediate`, writes the log, results and HTML report under `/var/log/scap` and optionally fetches them to the control node. When a product cannot live with a rule, the role renders an XCCDF tailoring that extends the profile and deselects that rule, recording owner, change control reference, review date and justification as comments in the file. This is how the reference implementation keeps hardened hosts honest: the baseline is CIS, every deviation is a named rule with a written reason, and the product roles ship their own tailorings (`vars/scap/cis.yml`) so the exceptions for Red Hat Identity Management (IdM), Red Hat Satellite, Red Hat build of Keycloak (RHBK), Red Hat Ansible Automation Platform (AAP) and RHEL image builder are reviewed per product rather than in one site-wide list.

SCAP is not a stage of `site.yml` on its own. Each product role runs this role at the end of its own stage when a `<role>_scap_profile` is set; the standalone `redhat_scap` playbook exists for hosts no product role covers.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.redhat_scap` when referencing this role.

## Requirements

- Managed node: RHEL 9 or 10 with `openscap-scanner` and `scap-security-guide` installed (both are in the base repositories; the datastream path is selected by major version).
- Collections used directly: none beyond `ansible.builtin`.
- No inventory groups are required. The collection playbook targets `redhat` and gathers facts; when composed, the role gathers the facts it needs itself.
- Golden images built by the site's image pipeline are expected to be hardened at build time; this role is the post-install pass that re-applies the baseline after a product has been installed.

## Dependencies and composition

The role composes nothing. It is composed through `include_role` by [`redhat_identity_management`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_identity_management/README.md), [`redhat_satellite`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_satellite/README.md), [`redhat_keycloak`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_keycloak/README.md), [`redhat_ansible_automation_platform`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_ansible_automation_platform/README.md) and [`redhat_image_builder`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_image_builder/README.md). Each passes `redhat_scap_tailoring_title`, `redhat_scap_tailoring_description` and `redhat_scap_tailoring_exceptions` from its `vars/scap/<profile>.yml`; `redhat_scap_profile` itself is read from inventory.

## Tags

The role defines no tags. Composing roles apply `scap` and their product tag (`idm_scap`, `satellite_scap`, `keycloak_scap`, `aap_scap`, `image_builder_scap`); the collection playbook adds `redhat` and `scap`.

- name: Red Hat Security Content Automation Protocol (SCAP)
  hosts: "{{ target_hosts | default('redhat') }}"
  gather_facts: true
  become: true
  tags:
    - redhat
    - scap
  roles:
    - infra.soe.redhat_scap

Site-wide settings in `group_vars/redhat` and a host-specific exception:

```yaml
redhat_scap_profile: xccdf_org.ssgproject.content_profile_cis
redhat_scap_report_dir: "{{ playbook_dir }}/../reports/"

redhat_scap_tailoring_exceptions:
  - name: xccdf_org.ssgproject.content_rule_service_cockpit_disabled
    status: deselected
    justification: Cockpit is the management interface of this host.
    owner: platform-team
    change_control: CC-2026-0042
    review_date: '2027-01-31'
```

## Security considerations

- `--remediate` changes the host: it applies every fix of every selected rule, from kernel parameters to PAM, SSH and auditd configuration. Run it against a profile you have tested on the product in question; the shipped tailorings list the rules that would break IdM, Satellite, RHBK, AAP and Image Builder.
- Each exception weakens the baseline. The role records justification, owner, change control and review date next to the rule so that an auditor can read the tailoring file alone; treat a missing justification as a defect.
- Results and the HTML report describe the host's configuration in detail; they are written with mode `0640` under a `0750` directory owned by root and, when fetched, land on the control node under `redhat_scap_report_dir`.
- `oscap` exits with code 2 when rules still fail after remediation; the role treats that as a change, not an error, so read the summary or the report.

## Operational notes

- A new set of files is written on every run (the timestamp is part of the file names); prune `redhat_scap_results_dir` on long-lived hosts.
- The tailoring is only rendered when `redhat_scap_tailoring_exceptions` is non-empty; otherwise the upstream profile is evaluated as is.
- Role variables from a product's `vars/scap/<profile>.yml` have higher precedence than inventory, so a product's shipped exceptions cannot be overridden from `group_vars`; add site exceptions through the standalone playbook or extend the shipped file.
- The role gathers a minimal fact set itself (`!all`), which provides `ansible_date_time` and `ansible_distribution_major_version` for the file names and the datastream path.
- Re-running after a change in exceptions is the way to re-select a rule: `status: selected` turns a deselected rule back on in the extended profile.
