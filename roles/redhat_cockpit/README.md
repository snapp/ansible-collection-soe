# Ⓐ Ansible Role: redhat_cockpit

Requests a TLS certificate for the host's `HTTP/` service principal from Red Hat Identity Management (IdM) through `infra.soe.redhat_idm_service` and, when enabled, installs and configures the Red Hat Enterprise Linux (RHEL) web console with `redhat.rhel_system_roles.cockpit`, unmasking its systemd units and labelling the console port for SELinux. The certificate stage is the useful part for most hosts: it runs whenever an IdM administrator password is available and leaves every enrolled host with an IdM-issued certificate under `/etc/pki/cockpit_idm_service/`, which is what makes the console (and anything else that serves HTTPS on the host) trusted by the site CA instead of self-signed.

Cockpit is the seventh stage of `site.yml`, after IdM client enrolment and before Satellite, and runs on every RHEL host outside the `identity_management` and `satellite` groups, whose products serve their own consoles.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.redhat_cockpit` when referencing this role.

## Requirements

- Managed node: RHEL 9 or 10 enrolled in IdM (`infra.soe.redhat_idm_register`) when the certificate stage is enabled.
- Collections used directly: [`redhat.rhel_system_roles`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_system_roles/content/role/cockpit/) (`cockpit` role and `seport` module); through the certificate stage, [`redhat.rhel_idm`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_idm/).
- Inventory: the `cockpit_*` variables of the cockpit system role (`cockpit_packages`, `cockpit_enabled`, `cockpit_started`, `cockpit_port`, `cockpit_manage_firewall`, `cockpit_cert`, `cockpit_private_key`, ...), documented at the link above.
- No inventory groups are required. The collection playbook targets `redhat:!identity_management:!satellite`.

To serve the IdM certificate, point the system role at the files the certificate stage produces:

```yaml
cockpit_cert: /etc/pki/cockpit_idm_service/service.crt
cockpit_private_key: /etc/pki/cockpit_idm_service/private/service.key
```

## Security considerations

- The console listens on `cockpit_port` (9090 by default) and offers a full login to the host; the role labels the port for SELinux but does not open it in the firewall. Open it deliberately through the site's `firewall` definitions or the system role's `cockpit_manage_firewall`, and prefer reaching it through the Caddy reverse proxy with single sign-on.
- The IdM-issued certificate and key are owned by root with modes `0640` and `0600`; cockpit-ws runs as root for the TLS listener, so no further ownership change is needed.
- `redhat_cockpit_idm_admin_password` is handled by `infra.soe.redhat_idm_service` under `no_log`.
- Image Builder hosts run Cockpit for the Image Builder web interface; the matching CIS exception is documented in [`redhat_image_builder`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_image_builder/README.md).

## Operational notes

- Only `redhat_cockpit_enabled`, `redhat_cockpit_port` and the `redhat_cockpit_idm_*` options influence the tasks; `redhat_cockpit_started`, `redhat_cockpit_zone` and `redhat_cockpit_packages` are defined but not consumed. The system role's own `cockpit_*` variables control packages, service state and firewall.
- The SELinux label is applied to `redhat_cockpit_port`, but the decision whether that is needed reads the system role's `cockpit_port`; keep the two equal.
- Changing the SELinux port label notifies a `semodule -R` reload.
- Units are unmasked before installation because hardened images ship Cockpit masked.
