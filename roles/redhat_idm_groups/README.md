# Ⓐ Ansible Role: redhat_idm_groups

Creates or updates groups in Red Hat Identity Management (IdM) with `redhat.rhel_idm.ipagroup`: GID, description, member users and nested member groups. Groups are the unit of authorisation throughout the reference implementation. HBAC rules (`infra.soe.redhat_idm_hbac`) grant host access to groups, sudo rules (`infra.soe.redhat_idm_sudo`) grant privileges to groups, and the single sign-on realm in Red Hat build of Keycloak (RHBK) maps IdM groups into the `groups` claim that Caddy's forward-auth sidecars and the applications behind them authorise on.

The role is composed twice in the build order: by `infra.soe.redhat_identity_management` for the site-wide groups (`admins`, `service-accounts`, ...) right after IdM is installed, and by each product role for its own groups (`satellite-admins`, `keycloak-admins`, `aap-users`, `imagebuilder-users`) when that product is deployed.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.redhat_idm_groups` when referencing this role.

## Requirements

- Managed node: a Red Hat Enterprise Linux (RHEL) 9 or 10 host that is an IdM server or an enrolled client with the IdM Python libraries, because the `redhat.rhel_idm` modules run on the target.
- Collections used directly: [`redhat.rhel_idm`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_idm/) (`ipagroup`).
- An IdM administrator password in `redhat_idm_groups_admin_password`.

## Example playbook

```yaml
---

- name: Red Hat Identity Management (IdM) groups
  hosts: "{{ target_hosts | default('idm_server') }}"
  gather_facts: false
  become: true
  roles:
    - role: infra.soe.redhat_idm_groups
      redhat_idm_groups_admin_password: "{{ idm_admin_password }}"
      redhat_idm_groups:
        - name: admin-accounts
          description: Global Administrator Accounts
          users:
            - siteadmin
        - name: service-accounts
          description: Service Accounts
          gid: 1000800
          users:
            - ansible
            - satellite
```

## Security considerations

- The administrator password is passed as `ipaadmin_password`; the task runs under `no_log` (gated by `no_log_enabled`), which also hides the group definitions from the output.
- Groups are only ever ensured present; the role does not remove groups that disappear from inventory. Removing a group is a deliberate manual step, but removing a user from an item's `users` list does remove the membership.
- Membership in `admins` grants full IdM administration; keep that list short and in vaulted inventory where it names real people.

## Operational notes

- Idempotent through `ipagroup`. When an item sets `users` or `groups`, that list becomes the complete membership and members not listed are removed; when the key is omitted the membership is left alone.
- Nested groups via the `groups` key must exist before they are referenced; order the list accordingly or run twice.
- GIDs for service accounts are chosen deliberately in the site inventory so that they are stable across sites; see the site repository for the convention.
