# Ⓐ Ansible Role: local_users

Manages local accounts from a single list and dispatches to platform tasks by OS family. On Red Hat Enterprise Linux (RHEL) and Fedora it creates the group and user, an optional `/etc/sudoers.d` entry, the home directory with the right SELinux context and the `authorized_keys` file; on Windows it creates the user and installs administrators' public keys into the global `administrators_authorized_keys` file with restricted ACLs. Local accounts are the exception in the reference implementation, where identity lives in Red Hat Identity Management (IdM); this role exists for the two cases that cannot: the bootstrap account used to reach hosts before IdM exists (removed later by `infra.soe.redhat_identity_management`), and local service accounts that a product insists on, such as the `rhbk` account that `infra.soe.redhat_keycloak` creates through this role.

It is the first stage of `site.yml` and runs against every host, including Windows.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.local_users` when referencing this role.

## Requirements

- Managed node: RHEL 9 or 10, Fedora, or Windows with OpenSSH Server installed (the role writes `C:\ProgramData\ssh\administrators_authorized_keys`). Other OS families are silently skipped.
- Collections used directly: [`redhat.rhel_system_roles`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_system_roles/) (`sefcontext` module), [`ansible.windows`](https://console.redhat.com/ansible/automation-hub/repo/published/ansible/windows/) (`win_user`, `win_acl`, `win_acl_inheritance`), [`community.windows`](https://docs.ansible.com/ansible/latest/collections/community/windows/index.html) (`win_lineinfile`).
- No inventory groups are required; the collection playbook targets `all`.

## Dependencies and composition

The role composes nothing. It is composed by [`redhat_keycloak`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_keycloak/README.md), which passes `local_users` ← `redhat_keycloak_local_users`.

## Example playbook

This matches the collection's own [`playbooks/local_users.yml`](https://github.com/snapp/ansible-collection-soe/blob/main/playbooks/local_users.yml):

```yaml
---

- name: Local Users
  hosts: "{{ target_hosts | default('all') }}"
  gather_facts: false
  become: true
  tags:
    - redhat
    - fedora
    - microsoft
    - local_users
  roles:
    - infra.soe.local_users
```

A bootstrap account and a service account for RHEL hosts, in `group_vars`:

```yaml
local_users:
  - name: bootstrap
    uid: 1100
    group: bootstrap
    gid: 1100
    comment: Bootstrap Account
    home: /home
    sudo: 'ALL=(ALL) NOPASSWD: ALL'
    ssh_public_key: "{{ _vault_bootstrap_ssh_public_key }}"

  - name: rhbk
    uid: 900
    group: rhbk
    gid: 900
    comment: Keycloak Application Account
    home: /opt
    selinux_home_equivalent: false   # home is an application directory, not a user home
```

## Security considerations

- Sudo rules are written verbatim to `/etc/sudoers.d/<name>` with mode `0440`. The file is not run through `visudo -c`, so a syntax error locks sudo until fixed from the console; keep rules simple.
- Home directories are created with mode `0700`, `.ssh` with `0700` and `authorized_keys` with `0600`, all owned by the user. `restorecon` runs on every pass to keep the SELinux labels right.
- On Windows the `administrators_authorized_keys` file has inheritance removed and is readable by `Administrators` and `SYSTEM` only, as OpenSSH requires. Non-administrator Windows users receive no key.
- Windows passwords are passed to `win_user`, which marks the parameter `no_log` itself; keep them in Ansible Vault.
- Local accounts bypass IdM policy (password rules, HBAC, sudo rules). Limit them to the bootstrap and service accounts the site needs and let `redhat_identity_management` remove the bootstrap account once IdM login works.

## Operational notes

- The RHEL tasks create the user with `uid` taken from the item's `gid`; keep `uid` and `gid` equal, as every example in the collection does.
- `home` is the parent directory: a user `caddy` with `home: /var/lib` gets `/var/lib/caddy`.
- On RHEL the `uid`, `groups` and `shell` keys are accepted but ignored (`uid` because the `gid` value is used, the other two because the tasks never pass them on); `groups`, `password` and `state` are read on Windows only.
- `selinux_home_equivalent` adds a `sefcontext` substitution that labels the home like `/home/<name>`; disable it for service accounts whose home is `/opt` or `/var/lib`, otherwise the equivalence rule would shadow the application's own file contexts.
- On Windows the `groups` key must be present; the role tests it to decide whether to install the key for administrators.
- Facts are gathered with a minimal subset (`distribution`, `os_family`) only when the list is non-empty, so the role is cheap on hosts that define no users.
