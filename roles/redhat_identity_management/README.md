# Ⓐ Ansible Role: redhat_identity_management

Installs and configures Red Hat Identity Management (IdM), the root of trust of the reference implementation: its certificate authority signs every service certificate, its Kerberos realm and HBAC rules decide who may log in where, its sudo rules replace local privilege grants, and its integrated DNS is the site's name service. The role prepares the IdM hosts, installs the first server on the `idm_server` group and replicas on the `idm_replica` group with the `redhat.rhel_idm` roles, and then configures the realm once from the first server: global user defaults, the ACME service, users, groups, sudo and HBAC rules (through the `infra.soe.redhat_idm_*` roles), password policies for service and administrator accounts, DNS forwarders, forward zones and the server records in every managed DNS zone. Finally it removes the local bootstrap account once IdM login works, opens the IdM ports and applies the IdM-specific CIS tailoring.

IdM is the fifth stage of `site.yml`, after the hosts have local users, registration, storage and updates, and before anything that needs a certificate, an HBAC rule or a DNS name. A single server is a single point of failure by hardware footprint; the role supports replicas through the `idm_replica` group, and the `/etc/hosts` preparation exists so servers and replicas can find each other before IdM DNS is up.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.redhat_identity_management` when referencing this role.

## Requirements

- Managed node: Red Hat Enterprise Linux (RHEL) 9 or 10 sized for an IdM server, registered for content (`infra.soe.redhat_register`) and reachable by its final fully qualified host name.
- Collections used directly: [`redhat.rhel_idm`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_idm/) (`ipaserver`, `ipareplica`, `ipaclient` roles and the `ipaconfig`, `ipapwpolicy`, `ipadnsconfig`, `ipadnsforwardzone`, `ipadnszone`, `ipadnsrecord` modules); through composed roles also [`redhat.rhel_system_roles`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_system_roles/).
- Inventory groups: `idm_server` (first server; the configure stage runs on its first member) and optionally `idm_replica`.
- Installer inputs for the upstream roles in inventory: `ipaserver_*` (`ipaserver_domain`, `ipaserver_realm`, `ipaserver_setup_dns`, `ipaserver_forwarders`, `ipaserver_reverse_zones`, `ipaserver_setup_kra`, ...) and `ipareplica_*`, documented at the links above. This role only supplies the administrator password to them.
- Groups named `service-accounts` and `admin-accounts` in `redhat_idm_groups`, because the password policies are attached to them.

  hosts: "{{ target_hosts | default('idm_server:idm_replica') }}"

  become: true

## Security considerations

- The administrator password is the Directory Manager and admin password at installation and is used by every `redhat.rhel_idm` module through `module_defaults`; it is also piped to `kinit` through a shell under `no_log`. Keep it in Ansible Vault or an AAP credential injector.
- The cleanup stage is a point of no return: it deletes the local bootstrap account, its home and its `sudoers.d` entry on every host and then waits until an IdM account of the same name resolves with a UID of at least 1100 and has a sudo rule. Make sure `redhat_idm_users` contains that account and `redhat_idm_sudo_rules` grants it privileges before enabling `bootstrap_user`.
- The default firewall definition opens the full IdM port set, including the SMB, NetBIOS and RPC ports needed only for Active Directory trusts; trim `redhat_identity_management_firewall` on sites without a trust.
- The replica installation temporarily relaxes the login `umask` from `077` to `022` in `/etc/profile` and `/etc/bashrc` because the installer needs it, and restores it afterwards; a failed replica install can leave the relaxed value in place.
- The shipped CIS tailoring deselects rules that destroy an IdM server (removal of `bind`, `httpd` and `openldap-clients`, GSSAPI in SSH, and the authselect profile rules). Each exception has a justification and review date in [`vars/scap/cis.yml`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_identity_management/vars/scap/cis.yml).
- DNS forwarding uses policy `only`, so IdM never falls back to root servers; an empty `idm_global_forwarders` leaves the site without external resolution.

## Operational notes

- The configure stage runs once, on the first `idm_server` host; replicas receive everything through replication.
- The server records task loops `idm_dns_zones` without a default, and the global defaults task reads every `idm_default_*` value; both fail with an undefined variable when the inventory is incomplete.
- `idm_global_forwarders` configures the running IdM DNS; `ipaserver_forwarders` is the separate install-time input of the ipaserver role. Set both to the same list.
- Password policies are created with priority 0 (`service-accounts`) and 1 (`admin-accounts`); IdM requires the groups to exist first, which the groups sub-stage guarantees when they are in `redhat_idm_groups`.
- Re-running the role is safe: the installers detect an installed server, and the configure stage is idempotent apart from the Kerberos login, which always runs.
- After the cleanup stage the next play against a host may fail with a permission error on the bootstrap user's `~/.ansible/tmp`; the stage recreates the home from `/etc/skel`, but a controller that still holds the old connection needs to reconnect. This is tracked as a known issue in the code.
- `tasks/network.yml` is imported by `main.yml`; it is not a separate entry point.
