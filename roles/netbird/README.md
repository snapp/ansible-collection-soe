# Ⓐ Ansible Role: netbird

Deploys a self-hosted [NetBird](https://netbird.io) mesh VPN control plane as rootless Podman Quadlets under a dedicated service account, following NetBird's combined-server model: one `netbird-server` container (management, signal, relay, embedded STUN and the embedded Dex identity provider) and one dashboard container on their own container network, with the configuration rendered into the service account's home. TLS is terminated by `infra.soe.caddy` in front of the loopback-published ports, and Red Hat build of Keycloak (RHBK) is meant to be the external OpenID Connect connector behind the embedded identity provider, so VPN access is granted to the same Red Hat Identity Management (IdM) groups as everything else.

NetBird is the eleventh stage of `site.yml`, after Caddy. It is the remote-access edge of the reference implementation: peers reach the site over WireGuard tunnels brokered by this control plane, and the control plane itself is just another rootless container workload on a Podman host. The role runs as a rootless IdM user in the same style as `infra.soe.caddy`.

> [!NOTE]
> This role previously deployed four containers (`management`, `dashboard`, `signal`, `coturn`) wired directly to Keycloak. NetBird's architecture moved to an embedded Dex identity provider that brokers external OpenID Connect providers rather than letting the dashboard talk to them directly, and the old wiring stopped working once an unpinned deployment picked up that change. The role now follows NetBird's current combined-server model, confirmed against upstream's `infrastructure_files/getting-started.sh`, and pins both images.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.netbird` when referencing this role.

## Requirements

- Managed node: Red Hat Enterprise Linux (RHEL) 9 or 10 with Podman (`infra.soe.application_server`), enrolled in IdM, with the host trust bundle containing the IdM CA.
- The service account must exist with systemd lingering enabled before the role runs; the role does not create it. In the collection's own site it is created in IdM with a subordinate ID range through `infra.soe.redhat_idm_users` (`enable_subid: true`) and `infra.soe.redhat_idm_register` with SSSD subordinate IDs:

  ```console
  ipa user-add netbird --shell=/sbin/nologin --home=/var/lib/netbird
  loginctl enable-linger netbird
  ```

- Collections used directly: [`redhat.rhel_system_roles`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_system_roles/content/role/podman/) (`podman` role), [`community.general`](https://docs.ansible.com/ansible/latest/collections/community/general/index.html) (`sefcontext`), [`ansible.posix`](https://docs.ansible.com/ansible/latest/collections/ansible/posix/index.html) (`seboolean`; not yet declared as a collection dependency, install it alongside); through the meta dependency, `redhat.rhel_system_roles.firewall`.
- Inventory group `netbird`.
- One confidential RHBK client (`client_authenticator_type: client-secret`) with a `groups` protocol mapper, defined through [`redhat_keycloak`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_keycloak/README.md). Its single redirect URI is generated by NetBird's own dashboard when RHBK is added under Settings → Identity Providers; deploy first, capture that URI, then set the client's `redirect_uris`.
- A Caddy site block for `netbird_domain` (see below).

## Components

| Quadlet unit | Image | Role |
|---|---|---|
| `netbird.network` | – | Isolated bridge network shared by both containers |
| `netbird-server.volume` | – | Persists the SQLite store and keys |
| `netbird-server.container` | `netbirdio/netbird-server` | Management, signal, relay, embedded STUN and embedded identity provider (Dex), all on one internal port |
| `netbird-dashboard.container` | `netbirdio/dashboard` | Web UI; authenticates against netbird-server's own embedded issuer, not RHBK directly |

## Role variables

## Security considerations

- `config.yaml` (which contains the relay secret, the store encryption key and the cookie key) and `dashboard.env` are written with mode `0600`, SELinux type `container_file_t`, owned by the service account, under a `0750` directory; the render runs with `no_log`. The values never enter a unit file.
- The administrator API token is minted inside the server container with `netbird-server admin token create`, cached at `netbird_config_dir/.admin_api_token` with mode `0600` and read back under `no_log`. It grants full API access; delete the file to rotate it.
- The server and dashboard ports are published on loopback by default and reached only through Caddy on 443; STUN (3478/udp) and the WireGuard data plane (51820/udp) are published on all addresses because they cannot be proxied. The default firewall definitions open exactly those plus the DNS forwarder ports.
- Both images are pinned to a matched release pair; bump them together, never float on `latest`.
- `netbird_local_auth_disabled` stays false until single sign-on works; enabling it removes password login from the embedded identity provider.
- The service account's home outside `/home` is registered as `/home`-equivalent for SELinux so the rootless container store is labelled `container_file_t`; without it the confined container process is denied read on its own image layers.

## Operational notes

- Registering RHBK as the identity-provider connector is **not automated at the moment**: the tasks that would call `POST /api/identity-providers` are present in `tasks/main.yml` but commented out, so `netbird_idp_name`, `netbird_idp_issuer` and `netbird_idp_client_id` are unused and the connector is added in the dashboard under Settings → Identity Providers. The administrator token is still minted and cached for when the tasks are enabled.
- After the connector exists: log in through RHBK and confirm you land on `/peers`; copy the redirect URI NetBird generated into the RHBK client's `redirect_uris`; enable JWT group sync with claim `groups` under Settings → Groups; only then set `netbird_local_auth_disabled: true` and re-run.
- The dashboard always authenticates against the embedded issuer with the fixed internal client `netbird-dashboard`; this has nothing to do with the RHBK client and the two must not be confused.
- Everything (API, gRPC, relay, OpenID Connect) is served on the server container's single internal port 80; the reference Caddy block points every route except the dashboard catch-all at the same upstream.
- `netbird_trusted_reverse_proxies` must contain the source address the server actually sees for Caddy's requests; under rootless Podman networking that may be a gateway address rather than `127.0.0.1`. Check the server log for the client address of an incoming request.
- `netbird_manage_firewall` is not consulted by any task; the firewall is applied by the meta dependency and switched with `netbird_firewall_enabled`.
- Handlers restart `netbird-server.service` or `netbird-dashboard.service` in the service account's user scope when the respective configuration changes.
