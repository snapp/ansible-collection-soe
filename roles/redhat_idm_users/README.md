# Ⓐ Ansible Role: redhat_idm_users

Creates or updates user accounts in Red Hat Identity Management (IdM) with `redhat.rhel_idm.ipauser` and, for accounts flagged with `enable_subid`, generates a subordinate UID and GID range on the IdM server. IdM is the root of trust of the reference implementation, so every account that logs in to a host or runs a service is an IdM account: the site administrators, the `ansible` automation account that replaces the local bootstrap user, and the service accounts that products run under. The subordinate ID ranges matter for the latter: a service account such as `caddy` or `netbird` runs rootless Podman on an enrolled host, and SSSD hands the host the `subuid`/`subgid` range from IdM instead of a local `/etc/subuid` entry.

The role is composed by `infra.soe.redhat_identity_management` for the site-wide accounts right after IdM is installed, and by `infra.soe.redhat_satellite`, `infra.soe.redhat_keycloak`, `infra.soe.redhat_ansible_automation_platform` and `infra.soe.caddy` for their service accounts.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.redhat_idm_users` when referencing this role.

## Requirements

- Managed node: a Red Hat Enterprise Linux (RHEL) 9 or 10 host that is an IdM server or an enrolled client with the IdM Python libraries, because the `redhat.rhel_idm` modules run on the target.
- Collections used directly: [`redhat.rhel_idm`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_idm/) (`ipauser`).
- Inventory group `idm_server`: subordinate ID generation and its Kerberos login are delegated to its first member.
- An IdM administrator password in `redhat_idm_users_admin_password` and, for the delegated login, in the shared `idm_admin_password`.

## Example playbook

```yaml
---

- name: Red Hat Identity Management (IdM) users
  hosts: "{{ target_hosts | default('idm_server') }}"
  gather_facts: false
  become: true
  roles:
    - role: infra.soe.redhat_idm_users
      redhat_idm_users_admin_password: "{{ idm_admin_password }}"
      redhat_idm_users:
        - description: Ansible Automation Account
          name:
            username: ansible
            first: Ansible
            last: Automation
            full: Ansible Automation Account
          initials: AAA
          uid: 1100
          home: /home
          ssh_public_key: "{{ _vault_ansible_ssh_public_key }}"
        - description: Caddy Service Account
          name:
            username: caddy
            first: Caddy
            last: Service Account
            full: Caddy Service Account
          initials: CSA
          home: /var/lib/caddy
          shell: /sbin/nologin
          enable_subid: true
```

## Security considerations

- Passwords are set only when an account is created (`update_password: on_create`) and never rotated by Ansible; IdM's password policy expires administrator-set passwords so the user must change it at first login. Keep them in Ansible Vault.
- The user tasks run under `no_log` only for items that carry a `password`; items without one are shown in the output, which is intended because they contain nothing secret beyond a public key.
- The Kerberos login pipes `idm_admin_password` into `kinit admin` through a shell on the IdM server under `no_log`; the resulting ticket stays in the connecting user's credential cache on that server until it expires.
- `enable_subid` grants the account a 65536-wide subordinate ID range; only service accounts that run rootless containers need it.

## Operational notes

- `ipa subid-generate` is run once per flagged account and treated as unchanged when the server answers that a range already exists.
- `gid` is set to `uid` when omitted, matching IdM's user private group convention; omit both to let IdM allocate.
- Because the login and the subordinate ID generation are delegated to `groups['idm_server'][0]`, the role needs that group even when it runs against another host (a product host, for example).
- Removing an item does not remove the account; deletions are a manual step.
