# Ⓐ Ansible Role: caddy

Deploys [Caddy](https://caddyserver.com) as a rootless Podman Quadlet under a dedicated service account: the TLS-terminating reverse proxy in front of every self-hosted service of a site. Site blocks are supplied as raw Caddyfile fragments in `caddy_domains` and concatenated into the Caddyfile, so each service can publish its own block without the role knowing about it. The container mounts the host trust bundle, which is how Caddy trusts the Red Hat Identity Management (IdM) certificate authority for its backends and requests its own certificates from the IdM ACME directory, and the role lowers `net.ipv4.ip_unprivileged_port_start` so rootless Podman can bind ports 80 and 443. Optionally it deploys one [oauth2-proxy](https://github.com/oauth2-proxy/oauth2-proxy) sidecar per protected virtual host, so Caddy can put Red Hat build of Keycloak (RHBK) single sign-on in front of applications that have no OpenID Connect of their own.

Caddy is the tenth stage of `site.yml`, after RHBK and before NetBird. It presupposes IdM (for the `caddy` service account, the ACME directory and the trust bundle), RHBK (for the sidecars' clients) and a Podman host (`infra.soe.application_server`). It is the edge of the reference implementation: one rootless, unprivileged process terminates TLS for everything behind it, and everything behind it stays on private addresses.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.caddy` when referencing this role.

## Requirements

- Managed node: Red Hat Enterprise Linux (RHEL) 9 or 10 with Podman (`infra.soe.application_server`), enrolled in IdM, with the host trust bundle containing the IdM CA. The service account must exist with systemd lingering enabled; the users stage creates it in IdM and `infra.soe.redhat_idm_register` with SSSD subordinate IDs makes rootless Podman work for it.
- Collections used directly: [`redhat.rhel_system_roles`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_system_roles/content/role/podman/) (`podman` role), [`ansible.posix`](https://docs.ansible.com/ansible/latest/collections/ansible/posix/index.html) (`seboolean`; not yet declared as a collection dependency, install it alongside); through composed roles, [`redhat.rhel_idm`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_idm/).
- Inventory group `caddy`; an `idm_server` group when the IdM stage runs.
- For sidecars: a confidential RHBK client per protected application with a `groups` mapper (`full.path: false`) and an audience mapper, defined through [`redhat_keycloak`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_keycloak/README.md).

## Example playbook

This matches the collection's own [`playbooks/caddy.yml`](https://github.com/snapp/ansible-collection-soe/blob/main/playbooks/caddy.yml):

```yaml
---

- name: Caddy Transport Layer Security (TLS) Reverse Proxy
  hosts: "{{ target_hosts | default('caddy') }}"
  gather_facts: false
  become: true
  tags:
    - caddy
  roles:
    - infra.soe.caddy
```

`caddy_domains` is a list of Caddyfile fragments. The first entry is conventionally a shared snippet; the IdM ACME directory needs RSA keys because it rejects Caddy's default ECDSA keys:

```yaml
caddy_domains:
  - |
    (idm_caddy_acme_ca) {
      tls {
        ca https://idm1.mtj1.prod.example.org/acme/directory
        ca_root /etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
        key_type rsa4096
      }
    }
  - |
    git.mtj1.prod.example.org {
      import idm_caddy_acme_ca
      reverse_proxy http://10.1.10.11:3000
    }
```

A protected virtual host adds a sidecar and a site block that uses it:

```yaml
caddy_oauth2_proxies:
  - name: code                              # -> container and DNS name oauth2-proxy-code
    domain: code.mtj1.prod.example.org      # drives the redirect URI
    port: 4180                              # container-internal only; never published
    allowed_groups:
      - code-server-users                   # groups claim; no leading slash
    client_id: "{{ _vault_code_server_oauth_client_id }}"
    client_secret: "{{ _vault_code_server_oauth_client_secret }}"
    cookie_secret: "{{ _vault_code_server_cookie_secret }}"

caddy_domains:
  - |
    code.mtj1.prod.example.org {
      import idm_caddy_acme_ca
      route {
        handle /oauth2/* {
          reverse_proxy oauth2-proxy-code:4180
        }
        forward_auth oauth2-proxy-code:4180 {
          uri /oauth2/auth
          copy_headers X-Auth-Request-User X-Auth-Request-Email X-Auth-Request-Groups X-Auth-Request-Preferred-Username
          @unauthorized status 401
          handle_response @unauthorized {
            redir * /oauth2/start?rd={scheme}://{host}{uri}
          }
        }
        request_header -X-Auth-Request-User
        reverse_proxy http://10.1.10.11:8443
      }
    }
```

A complete worked site block for NetBird lives in [`roles/netbird/files/caddy_netbird.conf`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/netbird/files/caddy_netbird.conf).

## Security considerations

- Caddy runs rootless as `caddy_service_user`; the only root actions are the `container_read_certs` SELinux boolean, the `ip_unprivileged_port_start` sysctl (set to the lowest published host port, 80 by default, which lets every unprivileged process on the host bind ports from there up) and the configuration directory ownership.
- Sidecar credentials become Podman secrets (`oauth2-proxy-<name>-client-id`, `-client-secret`, `-cookie-secret`) injected as `OAUTH2_PROXY_*` environment variables; they never appear in a unit file, and the tasks that handle them run with `no_log`. The validation task is `no_log` under `no_log_enabled`.
- Sidecars publish no host port and are reachable only by container name over the private `caddy_network`; from any other host `curl http://<host>:4180/ping` must fail to connect.
- The Caddyfile is written with mode `0644` and SELinux type `container_file_t`; fragments may interpolate inventory variables, so do not put secrets in `caddy_domains`.
- The Caddy image is `docker.io/caddy:latest`, unpinned; the oauth2-proxy image is pinned. Pin Caddy through a site-specific fragment of the Quadlet if reproducibility matters more than updates.
- The default firewall definition opens 80/tcp, 443/tcp and 443/udp (HTTP/3).

## Operational notes

Things that will bite you with forward auth:

- Match `401`, not `4xx`. `/oauth2/auth` returns 401 for "no session" and 403 for "signed in, but not in `allowed_groups`". Redirecting a 403 to `/oauth2/start` bounces off the user's valid session and loops forever; let 403 reach the browser.
- Strip inbound identity headers inside `route { }`. `request_header` sorts after `forward_auth` in Caddy's default directive order, so outside a `route` block it would delete the very headers `forward_auth` just copied; `route` runs directives in written order.
- `allowed_groups` takes bare names. oauth2-proxy's documentation shows `--allowed-group=/name`, which assumes Keycloak's default full-path group claim; the realm's group mappers in this collection set `full.path: false`.
- `keycloak-oidc` requires an audience mapper on the RHBK client; without it every token is rejected as wrong-audience. See the client example in [`redhat_keycloak`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_keycloak/README.md).
- No health check on the sidecar: the default image is distroless, so an in-container probe cannot run. `/ping` is still served for external checks; use the `-alpine` tag if `HealthCmd` is needed.

Validate before you deploy. A malformed Caddyfile takes the whole proxy down, so check it first:

```console
podman run --rm -v ./Caddyfile:/etc/caddy/Caddyfile:ro,Z docker.io/caddy:latest caddy validate --config /etc/caddy/Caddyfile
```

`caddy adapt --config Caddyfile` prints the resulting JSON, the only reliable way to confirm that handlers ended up in the intended order.

Verify after you deploy:

```console
sudo -iu caddy
systemctl --user status caddy.service
podman exec caddy wget -qO- http://oauth2-proxy-code:4180/ping   # -> OK (name resolution works)
podman secret ls                                                  # the three oauth2-proxy secrets
```

Other notes:

- Address backends by their network address, not `127.0.0.1`: Caddy runs in a container, so loopback is its own network namespace, not the host's.
- Changing `caddy_domains` rewrites the Caddyfile and restarts the `caddy` user service through a handler; sidecar changes are applied by the podman role when the unit content changes.
- When `caddy_oauth2_proxies` is empty no network Quadlet is created and Caddy keeps Podman's default networking; adding the first sidecar later recreates the Caddy unit on the shared network.
- `caddy_acme_ca` is not consulted by any task; the ACME directory is whatever the fragments say.
