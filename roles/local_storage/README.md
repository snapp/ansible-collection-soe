# Ⓐ Ansible Role: local_storage

Grows the partition behind the LVM physical volume with `growpart`, so a hardened golden image that was built small uses the whole disk it is deployed onto, and then applies the volume group and logical volume layout from inventory through `redhat.rhel_system_roles.storage`. The layout is where the CIS-driven separation of `/home`, `/tmp`, `/var`, `/var/log`, `/var/log/audit` and `/var/tmp` with `nodev`, `nosuid` and `noexec` mount options is expressed, together with the service-specific volumes each product needs (for example `/var/lib/pulp` on Satellite, `/var/lib/aap` on Red Hat Ansible Automation Platform (AAP)).

In the `site.yml` build order the role runs third, after local users and Red Hat Enterprise Linux (RHEL) registration and before the update pass, so the volumes exist before packages are installed into them. Both steps are gated on their variable being defined; hosts without a layout in inventory are left untouched.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.local_storage` when referencing this role.

## Requirements

- Managed node: RHEL 9 or 10, or Fedora, with `cloud-utils-growpart` installed (`/bin/growpart`) and the `blivet` dependencies the storage role installs itself.
- Collections used directly: [`redhat.rhel_system_roles`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_system_roles/content/role/storage/) (`storage` role).
- No inventory groups are required; the collection playbook targets `redhat:fedora`, and the layouts live in each group's `group_vars`.

## Tags

The role defines no tags. The collection playbook adds the play tags `redhat`, `fedora` and `local_storage`.

## Example playbook

This matches the collection's own [`playbooks/local_storage.yml`](https://github.com/snapp/ansible-collection-soe/blob/main/playbooks/local_storage.yml):

```yaml
---

- name: Local Storage
  hosts: "{{ target_hosts | default('redhat:fedora') }}"
  gather_facts: false
  become: true
  tags:
    - redhat
    - fedora
    - local_storage
  roles:
    - infra.soe.local_storage
```

A layout in `group_vars/satellite_server/local_storage.yml`:

```yaml
local_storage_pv:
  device: /dev/vda
  partition: 4

local_storage_lv:
  - name: rootvg
    type: lvm
    disks:
      - /dev/vda4
    volumes:
      - name: rootlv
        size: 10 GiB
        mount_point: /
        fs_type: xfs
      - name: var_lib_pulplv
        size: 150 GiB
        mount_point: /var/lib/pulp
        fs_type: xfs
        mount_options: 'defaults,nodev,nosuid'
      - name: var_tmplv
        size: 5 GiB
        mount_point: /var/tmp
        fs_type: xfs
        mount_options: 'defaults,nodev,noexec,nosuid'
```

## Security considerations

- The storage role runs with its default `storage_safe_mode: true`, which refuses to remove or reformat existing devices and file systems; a layout change that would destroy data fails instead of proceeding. Override that variable only deliberately.
- Mount options such as `noexec` on `/tmp` and `/var/tmp` interact with installers: the Satellite SCAP tailoring in [`redhat_satellite`](https://github.com/snapp/ansible-collection-soe/blob/main/roles/redhat_satellite/README.md) documents why `satellite-installer` cannot run with `noexec` on those paths.
- `growpart` runs as root against the disk named in `local_storage_pv`; a wrong device or partition number is the main risk, so keep the values in `group_vars` next to the layout they belong to.

## Operational notes

- `growpart` is idempotent: it reports `NOCHANGE` when the partition already fills the disk, and the task only reports a change when the tool prints `CHANGED`.
- Growing the partition does not grow the physical volume or the file systems by itself; the storage role takes care of resizing the volumes listed in `local_storage_lv` to their requested sizes.
- Sizes in `local_storage_lv` are absolute, so a volume that is already larger than requested is left alone in safe mode. Use `size: 100%` style values only where the storage role documents them.
- A `growfs` key in `local_storage_pv` is accepted but ignored; file system growth is the storage role's job.
