# Ⓐ Ansible Role: redhat_idm_register

Enrols a Red Hat Enterprise Linux (RHEL) host as a client of Red Hat Identity Management (IdM) through `redhat.rhel_idm.ipaclient`: Kerberos, SSSD and the host keytab are configured, home directories are created at first login and SSSD becomes the source of subordinate ID ranges for rootless containers. Every option falls back to a shared `idm_*` inventory variable, so a site states the realm once and this role carries the values into the ipaclient role.

Enrolment is the sixth stage of `site.yml`, right after `infra.soe.redhat_identity_management` has installed the servers, and everything that follows presupposes it: `infra.soe.redhat_idm_service` can only request certificates on an enrolled host, HBAC and sudo rules only apply to enrolled hosts, and the zero-trust provisioning story of the reference implementation starts the moment a host has a keytab. The collection playbook targets every RHEL host outside the `identity_management` group, since the servers and replicas enrol themselves during installation.

> [!NOTE]
> Use the Fully Qualified Collection Name `infra.soe.redhat_idm_register` when referencing this role.

## Requirements

- Managed node: RHEL 9 or 10 that can resolve the IdM realm's DNS SRV records (or has `ipaclient_servers` set) and reach the IdM servers on the Kerberos, LDAP and HTTPS ports.
- Collections used directly: [`redhat.rhel_idm`](https://console.redhat.com/ansible/automation-hub/repo/published/redhat/rhel_idm/content/role/ipaclient/) (`ipaclient` role).
- Inventory: the shared `idm_domain` and `idm_admin_password` variables (or their role-prefixed equivalents), and any further `ipaclient_*` variables the ipaclient role documents (for example `ipaclient_servers`, `ipaclient_realm`, `ipaclient_hostname`).
- An IdM server (`infra.soe.redhat_identity_management`) that is up.

## Example playbook

This matches the collection's own [`playbooks/redhat_idm_register.yml`](https://github.com/snapp/ansible-collection-soe/blob/main/playbooks/redhat_idm_register.yml):

```yaml
---

- name: Red Hat Identity Management (IdM) Client Registration
  hosts: "{{ target_hosts | default('redhat:!identity_management') }}"
  gather_facts: false
  become: true
  tags:
    - redhat
    - idm_register
  roles:
    - infra.soe.redhat_idm_register
```

Realm-wide values in `group_vars/all` and `group_vars/redhat`:

```yaml
idm_domain: prod.example.org
idm_admin_password: "{{ _vault_idm_admin_password }}"
idm_client_subid: true
idm_client_mkhomedir: true
idm_client_all_ip_addresses: false
```

## Security considerations

- Enrolment writes the host keytab to `/etc/krb5.keytab` and configures SSSD for the realm; from then on host access is governed by IdM HBAC and sudo rules, which is the intended trust boundary.
- The enrolment principal is `admin` by default. A dedicated principal with only the host enrolment privilege (`idm_admin_user`) limits what a leaked `idm_admin_password` can do.
- `redhat_idm_register_force_join` replaces the keytab of an existing host entry; keep it off except when re-provisioning a host that kept its name, so a rogue host cannot take over an entry.
- `redhat_idm_register_all_ip_addresses` publishes every interface address in IdM DNS, including management or storage networks; leave it off unless those names should resolve.

## Operational notes

- The role gathers the `min` fact subset itself, so plays can keep `gather_facts: false`.
- The ipaclient role is idempotent on an enrolled host and exits early; a half-finished enrolment needs `redhat_idm_register_allow_repair: true` for one run.
- With `redhat_idm_register_domain` unset, the ipaclient role discovers the domain and servers from DNS, which only works once the host's resolver points at IdM DNS.
- Subordinate IDs through SSSD (`redhat_idm_register_subid`) require the account's range to exist in IdM (`enable_subid` in `infra.soe.redhat_idm_users`).
